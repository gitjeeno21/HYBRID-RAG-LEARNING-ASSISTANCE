# Interview guide: Hybrid RAG Assistant

How to explain the engineering decisions in this project, with the measured evidence behind each one. Every number links to a report generated by a script in `eval/`; none is an estimate.

## 30-second summary

A local RAG system over research PDFs. Answers come only from retrieved passages, with page citations that are checked automatically. Retrieval is hybrid: BM25 plus dense embeddings, merged with Reciprocal Rank Fusion. What sets it apart is the evaluation. A zero-LLM retrieval harness with page-level gold labels, bootstrap confidence intervals, and a dev/test split with a pre-registered adoption rule drove every retrieval decision, including the decision *not* to ship a reranker.

## Why hybrid retrieval?

Because the two retrievers fail on different questions. On the held-out set ([RETRIEVAL_COMPARISON.md](eval/RETRIEVAL_COMPARISON.md)):

| Question type | Dense | BM25 | Hybrid |
|---|---|---|---|
| exact term (numbers, names) | 9/12 | 12/12 | 12/12 |
| paraphrase (no shared words) | 12/13 | 6/13 | 10/13 |

Dense embeddings capture meaning but give little weight to a number like "9.5" or a symbol like "N = 6". MiniLM also only embeds the first 256 tokens of a chunk. BM25 matches literal tokens precisely but cannot match a paraphrase.

**What I would say honestly:** hybrid clearly beats dense-only (dev: 9 questions better, 0 worse; nDCG@5 better on both sets with CIs excluding zero). On *this* corpus it is not significantly better than BM25 alone, because technical PDFs are full of exact terms. Its value is robustness: it is never the worst retriever on any question type.

## Why RRF?

The scores are incomparable: cosine similarity is bounded, BM25 is unbounded and depends on corpus statistics. Normalising and averaging them means inventing a weighting. RRF uses only ranks, `score = Σ 1 / (60 + rank)`, so it needs no calibration and one over-confident list cannot dominate. k = 60 comes from the original paper and was fixed before any measurement. The trade-off, visible in the data: RRF rewards agreement, so a passage ranked first by only one retriever can be outvoted. That is why hybrid finds 2 fewer paraphrases than dense alone.

## Why is reranking useful, and why is it off?

A cross-encoder reads the query and passage *together*, so it scores relevance far better than comparing two independent embeddings. It is also too slow to run over the whole corpus, so it reranks only the fused top 10.

I measured it rather than assuming it helps:

- **MiniLM cross-encoder:** the biggest held-out gain (nDCG@5 +0.067, CI excludes zero). But it *loses* on dev (3 better, 4 worse), even after I fixed the dev labels that had made the loss look like an artefact. Cost: about 0.47 s per query on CPU.
- **BGE-reranker-base:** doesn't lose on dev, but its held-out gain is one question, at about 3 s per query on CPU.

My adoption rule says: don't lose on dev, and improve the held-out set. Neither passed cleanly, so both are behind a switch (`RAG_RERANK=1`, `RAG_RERANKER_MODEL`). On a GPU I would re-test BGE on a fresh question set.

## How does chunking affect retrieval?

- **Size:** an 8-configuration grid picked 1500 characters with 50 overlap. 1000-character chunks lost on the held-out set (2 better, 5 worse) and on multi-hop coverage ([ABLATION.md](eval/ABLATION.md)).
- **Embedding window:** MiniLM sees only 256 tokens, about 1000 characters, so the end of a 1500-character chunk is invisible to dense search. In 12 of 47 questions the answer sat past that point. BM25 covers it, which is part of why hybrid works. A 512-token model (bge-small) helped dense search but not the final hybrid ranking, so it was rejected.
- **Page boundaries:** chunks never cross pages, so citations stay exact. Cross-page chunking was tested; its apparent gain came from a scoring bias (a chunk spanning pages 4–5 got credit for both), and keyword scoring showed 0 better, 3 worse.
- **The bug that mattered most was downstream of chunking.** Pages hold two or more chunks, and the app de-duplicated passages *by page label*, silently dropping the second chunk. That is often the one with the answer. Fixing it raised "full gold evidence reaches the prompt" from 35/47 to 40/47 ([CONTEXT_COVERAGE.md](eval/CONTEXT_COVERAGE.md)). Lesson: measure what the *model receives*, not just what the retriever ranks.

## How are hallucinations controlled?

Layered, and each layer is measured:

1. **Grounded prompt:** answer only from the context. When it holds none of the answer, reply with one fixed refusal sentence; when it holds part, answer that part and name the gap. The fixed sentence makes refusals machine-detectable.
2. **Citation validation, deterministic:** every `file, p. X` the answer cites must be one of the retrieved pages. Violations are flagged in the UI.
3. **Support check:** one extra LLM call grades the answer SUPPORTED / PARTIAL / UNSUPPORTED against the passages, combined with retrieval strength into a confidence label. I report honestly that it is *not shown to be calibrated*, and it costs half the tokens of each answer.
4. **What I chose not to build:** a retrieval-score abstention gate. No score separates unanswerable questions (held-out AUC 0.61–0.72), and the prompt already refuses 13/13, so a gate could only add false refusals ([ABSTENTION_SIGNALS.md](eval/ABSTENTION_SIGNALS.md)).

**Measured effect** on the held-out set, with the same models before and after ([ANSWER_QUALITY_k5_stage4.md](eval/ANSWER_QUALITY_k5_stage4.md)):

- Correct answers 38/47 → **41/47**: 3 better, **0 worse**. The three are exactly the questions whose answer chunk the de-duplication bug used to drop, so a retrieval fix shows up as answer quality.
- False refusals 9/47 → **4/47**. All four remaining are retrieval misses, where refusing is the honest answer. Two multi-hop questions moved from refusal to a partial answer that names the gap.
- The cost: strict correct refusals 13/13 → 12/13. On review, the 13th answer says the roadmap "does not mention containerizing the API with Docker". It is correct and invents nothing, but it doesn't use the fixed refusal sentence. I report both readings.
- 93% of answer sentences are supported by the passages (judge model). The citation check also caught a live answer citing a page it was never given.

## How is retrieval quality evaluated?

- **Gold labels at page level, with verbatim evidence quotes** checked against the PDF text by a validator. The old metric ("any chunk from the right PDF containing a keyword") was too lenient.
- **Metrics:** Hit@k, MRR@10, Precision@k, Recall@k (per fact, so multi-hop questions need every fact), nDCG@k.
- **Statistics:** 95% bootstrap CIs and *paired* deltas with better/worse counts. With about 50 questions a CI spans about ±10 points, so I lead with paired counts.
- **Discipline:** decide on dev, confirm on held-out, under a rule fixed in advance. The harness blocks the LLM client at import, so retrieval experiments cannot spend quota, and it uses its own index, so experiments can never change what the app serves.

## Making it multi-user: what changed and why

**Q: How do you stop one user from seeing another user's documents?**
Login alone doesn't do it: with one shared index, every logged-in user could search everyone's PDFs. Isolation is enforced at the storage layer:

- **Files:** a private folder per user, with paths built only from the signed-in user's ID and a validated bare filename.
- **Dense index:** one shared Chroma collection, with every chunk tagged `user_id`. Code never touches the raw store. A `ScopedStore` wrapper adds the user's filter to *every* search, read, write and delete, and it overwrites any `user_id` a caller tries to set. Forgetting the filter is impossible by construction.
- **Lexical index:** BM25 is built per user from that user's chunks only.
- **Defence in depth:** fusion only accepts dense hits that map onto the user's own chunk list.
- **Proof:** an end-to-end test with real PDFs, embeddings and Chroma. Two users hold secret tokens, and every cross-user path is attempted, including same-named files and path traversal.

**Q: Why a middleware rather than a login check on each route?**
Secure by default. One middleware requires a session for every `/api` route except sign-in. A test sweeps all routes anonymously and expects 401, so a route added later cannot be left open by accident.

**Q: Sessions or JWT?**
Server-side sessions. A random token in an `HttpOnly` cookie can't be read by page scripts, the database stores only its SHA-256, and sign-out really revokes it. A stateless JWT can't be revoked before it expires, and this app has a database anyway. CSRF uses a per-session double-submit token, and `SameSite=Lax` adds a second layer.

**Q: How do you protect the shared API key?**
Each user has a daily token allowance, counted from the provider's own usage figures and checked before any LLM call starts. Retrieval-only features keep working when the allowance is spent. Measured cost per answer is about 5,300 tokens, half of it for the grounding check. On Groq's free tier (about 8k tokens per minute) that limits throughput to about one answer per minute, which is a concrete argument for making the grounding check optional.

## Technical challenges solved

| Challenge | What I did |
|---|---|
| Passages silently dropped before the prompt | Found by measuring evidence-in-prompt; fixed de-duplication. Evidence fully in the prompt: 35/47 → 40/47 |
| "Cosine" scores that were not cosine | Chroma stores squared L2, and LangChain's relevance score is √2·cos − 0.414 (it can go negative). Converted to true cosine, verified against directly computed embeddings, and restated the trust cut-offs in honest units |
| Dense and BM25 indexes drifting apart | Startup now verifies both hold the *same chunks*, not just the same count |
| Upload froze the server | CPU-bound indexing ran inside an `async` endpoint on the event loop; moved it to the thread pool |
| Free-tier rate limits | Shared client with backoff; the evaluation caches every LLM output and paces itself under the per-minute token limit |
| Seeing *why* an answer came out as it did | Pipeline trace on every answer (per-stage ms, tokens), plus a retrieval inspector showing each candidate's dense rank, BM25 rank and RRF score |
| Turning a single-user tool into a multi-user product | Accounts, sessions, CSRF, throttling; per-user storage, BM25 and a scoped vector store; per-user token allowance; isolation proven end to end |

## Limitations that remain

- **Small evaluation sets** (47 and 50 questions): only large effects are detectable. Held-out labels are machine-validated but not yet human-reviewed.
- **Two held-out PDFs (`ML111.pdf`, `ML222.pdf`) are not in the repository**, so 18 held-out questions cannot be reproduced from a clone.
- **The held-out set has been looked at many times now.** Further decisions should use a fresh set.
- **The confidence label is not shown to be calibrated,** and its grounding check uses the same model family that wrote the answer.
- **Local deployment:** no email verification or password reset, no HTTPS of its own (it needs a reverse proxy), and SQLite plus in-memory login throttling assume a single server process.
- **Cold start:** the first request after startup takes about 17 s (embedding model load plus building that user's BM25 index); later requests take milliseconds. BM25 indexes are kept in memory for the 16 most recently active users.
- **Upload is synchronous:** indexing runs in the server's thread pool (it no longer blocks other requests), but the upload request waits for it. A background job queue with progress reporting would be the next step for large files.
- **PyPDF text extraction:** no table structure or OCR; scanned PDFs would need an OCR step.
